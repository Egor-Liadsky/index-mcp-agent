# index-mcp-agent

Локальный индекс конспектов `.docx` для поиска по смыслу. `index-mcp`
читает каталог с `.docx`, режет текст на чанки двумя стратегиями
(`fixed` и `structure`), получает эмбеддинги у локального
[Ollama](https://ollama.com) и складывает чанки с векторами в SQLite. Вторая
команда сравнивает стратегии на вопросах к конспектам и пишет отчёт
`docs/chunking-comparison.md`.

Внешних сервисов, кроме Ollama, нет: ни Python, ни FAISS, ни облачных API.
Ближайшие соседи ищутся перебором косинусом в Rust. Команда `serve`
поднимает MCP-сервер на stdio с инструментами `index_search`,
`index_status`, `index_models`, `index_build` и `index_compare`: сервер
живёт в каталоге `mcp/` зонтичного репозитория
[agent](https://github.com/Egor-Liadsky/agent), и консольный клиент
`agentcli` пользуется им как процессом (cargo-зависимости между ними нет).

## Устройство

Cargo workspace (Rust edition 2024) из одного крейта:

| Крейт       | Каталог        | Что это                         |
|-------------|----------------|---------------------------------|
| `index-mcp` | `crates/index` | бинарник `index-mcp`: `build`, `compare` и `serve` |

- `src/main.rs` — флаги CLI, обход каталога, индексатор (чанки →
  эмбеддинги → хранилище) и команда `compare`;
- `src/docx.rs` — абзацы `.docx` с уровнем заголовка и смещениями;
- `src/chunk/mod.rs` — трейт `Chunker`, реестр стратегий и метрики границ;
- `src/chunk/units.rs` — единицы длины (`Units`) и разметка `Measure`;
- `src/tokens.rs` — счёт токенов WordPiece по словарю модели из Ollama;
- `src/chunk/fixed.rs`, `src/chunk/structure.rs` — две стратегии;
- `src/embed.rs` — клиент `POST /api/embed` Ollama;
- `src/store.rs` — SQLite через `sqlx`, миграции в `migrations/`;
- `src/compare.rs` — метрики, hit@k, MRR и отчёт в Markdown;
- `src/serve.rs` — MCP-сервер (`rmcp`): инструменты поверх `run_build` и
  `run_compare`, логика chunking, эмбеддинга и хранилища не дублируется;
- `src/search.rs` — поиск перебором косинусом со сверкой модели;
- `src/ollama.rs` — список моделей с эмбеддингами и размерность модели.

| Назначение           | Крейты                         |
|----------------------|--------------------------------|
| Асинхронный рантайм  | `tokio`                        |
| CLI                  | `clap`                         |
| Чтение `.docx`       | `zip`, `quick-xml`             |
| Счёт токенов         | `unicode-normalization` (NFD)  |
| HTTP к Ollama        | `reqwest` (rustls)             |
| MCP-сервер           | `rmcp` (server, macros, transport-io) |

| Сериализация, ошибки | `serde`, `serde_json`, `anyhow`|

Стратегия — реализация трейта `Chunker` (`name`, `params`, `chunk`).
Индексатор, эмбеддер и хранилище работают со списком `Box<dyn Chunker>`,
поэтому новая стратегия — это файл в `src/chunk/` и строка в `chunk::make`,
без правок остального кода.

## Установка и запуск

```bash
ollama pull nomic-embed-text                # один раз
cargo build --release

./target/release/index-mcp build --input ~/notes --db index.db --strategy all
./target/release/index-mcp compare --db index.db --questions questions.json
```

`build` печатает по строке на стратегию: число чанков, файлов, символов и
время эмбеддинга. `compare` печатает отчёт и записывает его в `--out`.

Проверка базы после `build`:

```bash
sqlite3 index.db "select strategy, count(*) from chunks group by strategy;
  select count(*) from chunks c left join embeddings e using(chunk_id) where e.chunk_id is null;
  select distinct model, dim from embeddings;"
```

Второе число — 0 (у каждого чанка есть вектор), третий запрос — одна строка
`nomic-embed-text|768`.

### `build`

| Флаг            | Умолчание    | Что задаёт |
|-----------------|--------------|------------|
| `--input`       | —            | каталог с `.docx`, обходится рекурсивно; скрытые каталоги и lock-файлы `~$*.docx` пропускаются |
| `--db`          | `index.db`   | файл SQLite, создаётся при первом запуске |
| `--strategy`    | `all`        | `fixed`, `structure` или `all` |
| `--unit`        | `chars`      | единица размеров ниже: `chars` (символы) или `tokens` (токены модели) |
| `--chunk-size`  | `1200`       | `fixed`: размер окна |
| `--overlap`     | `200`        | `fixed`: перекрытие окон, меньше половины окна |
| `--max-section` | `1500`       | `structure`: потолок длины чанка; раздел длиннее режется по абзацам |
| `--min-section` | `200`        | `structure`: кусок короче склеивается со следующим |
| `--min-chars`   | `50000`      | минимальный объём корпуса; меньше — ошибка с числом символов |

### `serve`

`index-mcp serve --db index.db` — MCP-сервер на stdio (JSON-RPC через
stdin/stdout). Флаги: `--db` (умолчание `index.db`), `--strategy` (стратегия
поиска, если `strategy` не передан), `--ollama-url`, `--model`,
`--doc-prefix`, `--query-prefix`, `--batch`, `--num-ctx` с теми же
умолчаниями, что у `build`. Модель `--model` — модель запроса `index_search`
и умолчание модели `index_build`; `--rewrite-model` задаёт отдельную Ollama
модель для query rewrite. Флага `--dim` нет: размерность берётся из
базы (поиск) или у модели (сборка). Ход сборки печатается в stderr, stdout
занят протоколом.

Инструменты. Имена и поля JSON — общий контракт с клиентом; результат —
JSON в `structuredContent` (тот же JSON дублируется текстом), ошибка —
`isError` с текстом на русском.

| Инструмент      | Пишет | Аргументы | Результат |
|-----------------|-------|-----------|-----------|
| `index_search`  | нет   | `query`; `strategy` (`fixed`/`structure`); `top_k` (5, максимум 20); `candidate_top_k` (20, максимум 100); `similarity_threshold` (-1…1, по умолчанию выключен); `rewrite` (false) | `{query, used_query, strategy, model, dim, top_k, candidate_top_k, similarity_threshold, rewrite, rewrite_fallback, candidates, results, hits:[{chunk_id, source, section, score, text}]}`, `score` — cosine |
| `index_status`  | нет   | — | `{db, exists, search_model, strategies:[{strategy, chunks, files, chars, model, dim, embed_ms, built_at, params}]}`; базу не создаёт |
| `index_models`  | нет   | — | `{models:[{name, dim, context_length, size}]}` — модели Ollama с capability `embedding` (`/api/tags` + `/api/show`) |
| `index_build`   | базу  | `input` (обязателен); `strategy`, `unit` (`chars`/`tokens`), `chunk_size`, `overlap`, `max_section`, `min_section`, `min_chars`, `model`, `num_ctx`, `batch`, `dim` | `{db, model, dim, strategies:[{strategy, chunks, files, chars, embed_ms}]}` |
| `index_compare` | отчёт | `questions`, `out` (оба обязательны); `top_k` (5); `candidate_top_k` (20); `similarity_threshold` (0.5 для filter-режимов); `rewrite_model` | `{out, report}` |

`index_build` не переданное берёт из умолчаний `build` (таблицы выше);
модель, адрес Ollama, `num_ctx` и `batch` — из флагов `serve`.

Порядок поиска: исходный запрос или его rewrite эмбеддится, все чанки
сортируются по cosine, берутся первые `candidate_top_k`, затем применяется
`similarity_threshold`. Среди оставшихся кандидатов чанки с дословными
многословными фразами из кавычек `„…“`, `«…»` или `"…"` ставятся выше,
после чего выдача ограничивается `top_k`. Внутри каждой группы порядок по
cosine; поле `score` и порог по-прежнему обозначают только cosine. Это
помогает запросам с точной фразой, когда нужный чанк уже попал в кандидаты;
фраза вне `candidate_top_k` не добавляется. `compare` использует то же
ранжирование для базовых метрик и всех режимов, включая rewrite.
У `index_search` аргумент `rerank: false` отключает перестановку по точным
фразам; по умолчанию она включена.
При ошибке `/api/chat`, пустом или невалидном ответе rewrite поиск продолжает
работу с исходным запросом и записывает причину в `rewrite_fallback`.

В самом MCP-сервере `index_search` без `similarity_threshold` не фильтрует
выдачу. Клиент `agentcli` в обычном режиме RAG передаёт настроенный порог,
а если он не задан — `0.5`; клиент не позволяет модели понизить этот минимум.
В режиме простого RAG он отключает порог и реранжирование.
Порог `index_compare` по умолчанию также равен `0.5` в режимах `filter` и
`rewrite+filter`.

Поиск отказывает, а не смешивает модели: если `--model` не совпала с моделью
векторов стратегии (`builds.model`, а затем и `embeddings.model` каждого
чанка), `index_search` возвращает ошибку «построена моделью X … векторы
несравнимы» до обращения к Ollama. Если в базе несколько стратегий, а
`strategy` и `--strategy` не заданы, это тоже ошибка.

### `compare`

| Флаг          | Умолчание                     | Что задаёт |
|---------------|-------------------------------|------------|
| `--db`        | `index.db`                    | база, построенная `build` |
| `--questions` | `questions.json`              | вопросы с ожидаемыми разделами |
| `--out`       | `docs/chunking-comparison.md` | куда записать отчёт |
| `--top-k`     | `5`                           | число результатов после фильтрации |
| `--candidate-top-k` | `20`                      | число кандидатов до фильтрации |
| `--similarity-threshold` | нет                  | threshold для filter-режимов; cosine от -1 до 1 |
| `--rewrite-model` | модель эмбеддингов            | Ollama-модель query rewrite |

### Общие флаги эмбеддинга

| Флаг             | Умолчание                | Что задаёт |
|------------------|--------------------------|------------|
| `--ollama-url`   | `http://localhost:11434` | адрес Ollama |
| `--model`        | `nomic-embed-text`       | модель эмбеддингов |
| `--doc-prefix`   | `search_document: `      | префикс задачи перед текстом чанка |
| `--query-prefix` | `search_query: `         | префикс задачи перед вопросом |
| `--batch`        | `32`                     | текстов в одном запросе |
| `--num-ctx`      | `2048`                   | контекст модели, `options.num_ctx`; обученный контекст модели он не расширяет |
| `--dim`          | `768`                    | ожидаемая размерность; другая — ошибка |

`compare` отказывается работать, если база построена другой моделью или
размерностью, чем указаны флаги: векторы разных моделей несравнимы.
Отчёт прогоняет один набор вопросов по режимам `baseline`, `rewrite`, `filter`
и `rewrite+filter`, отдельно показывает hit@1, hit@k, MRR, пустые результаты,
случаи полной фильтрации, средние размеры кандидатов/выдачи и параметры.

## Размеры в символах или токенах

`--unit` задаёт, в чём меряются `--chunk-size`, `--overlap`, `--max-section`
и `--min-section`. Числа умолчаний одни и те же, поэтому с `--unit tokens`
размеры обычно задают явно:

```bash
index-mcp build --input ~/notes --unit tokens --chunk-size 400 --overlap 50 \
  --max-section 600 --min-section 60
```

- `chars` — символы текста (умолчание);
- `tokens` — токены `nomic-embed-text`. Словарь берётся у Ollama
  (`POST /api/show` с `verbose: true`), считается токенизатором WordPiece
  так же, как Ollama режет вход модели. Токены — ровно то, что ограничивает
  контекст модели, поэтому в этом режиме `build` до чтения корпуса
  проверяет: самый большой чанк плюс префикс задачи и `[CLS]`/`[SEP]` не
  больше `--num-ctx`;
- размер относится к тексту чанка, включая дописанный заголовок
  продолжения, но без префикса задачи;
- граница разреза по-прежнему ищется у конца предложения или пробела, поэтому
  чанк бывает немного короче заданного размера, а перекрытие — немного
  меньше.

В отчёте длины чанков — в символах, единица построения записана в
параметрах стратегии (`"unit"`).

## Стратегии chunking

**`fixed`** — окна по `--chunk-size` символов с перекрытием `--overlap`.
Конец окна ищется в его последней четверти: сначала конец предложения или
абзаца, затем пробел, и лишь без них — жёсткий разрез. Начало следующего
окна — начало предложения рядом с точкой «конец минус перекрытие», иначе
начало слова. `section` — путь последнего заголовка перед началом чанка.

**`structure`** — раздел от заголовка до следующего заголовка того же или
более высокого уровня, вместе с подразделами:

- раздел целиком не длиннее `--max-section` — один чанк;
- длиннее — собственный текст раздела (заголовок и абзацы до первого
  подраздела) режется по границам абзацев, подразделы — рекурсивно тем же
  правилом; абзац длиннее `--max-section` режется по концам предложений;
- кусок короче `--min-section` склеивается со следующим куском того же
  родителя, последний — с предыдущим, если склейка не длиннее
  `--max-section`; иначе он остаётся отдельным чанком. `section` склейки —
  раздел её большей части, чтобы заголовок с одной вводной фразой не
  забирал себе текст первого подраздела;
- заголовок входит в текст чанка, а продолжению длинного раздела
  дописывается первой строкой; `char_start`/`char_end` указывают на
  фрагмент документа без дописанного заголовка;
- `--max-section` — потолок всего текста чанка, включая дописанный
  заголовок: этот текст целиком уходит в модель и должен поместиться в её
  контекст.

Текст до первого заголовка получает пустой `section`.

`chunk_id` — `{strategy}:{имя файла без расширения}:{ordinal:04}`, `ordinal`
считается внутри файла. Повторный `build` на тех же файлах и флагах даёт те
же id. Одинаковые имена файлов в разных подкаталогах — ошибка: id совпали бы.

## Схема БД

```sql
chunks (chunk_id TEXT UNIQUE, strategy, source, title, section, ordinal,
        char_start, char_end, text, crosses_section, cut_mid_sentence)
embeddings (chunk_id → chunks, model, dim, vector BLOB)   -- f32 little-endian
builds (strategy PRIMARY KEY, model, dim, files, chars, chunks, embed_ms,
        params, built_at)
```

- `source` — путь к файлу, `title` — `dc:title` из `docProps/core.xml`,
  иначе имя файла; `section` — путь заголовков `Раздел > Подраздел`;
  смещения — в символах общего текста документа (абзацы через `\n`);
- в `text` префикс задачи не пишется, он уходит только в модель;
- `crosses_section` и `cut_mid_sentence` считаются при построении: после
  него структуры документа в базе нет;
- `builds` хранит последнее построение стратегии: объём корпуса, время
  эмбеддинга и параметры (размеры стратегии, `doc_prefix`, `num_ctx`);
- `build` стратегии заменяет её строки одной транзакцией, другие стратегии
  не трогает. Эмбеддинг идёт до транзакции, поэтому недоступный Ollama
  оставляет прежний индекс целым.

## Сравнение и `questions.json`

```json
[
  { "question": "Чем TCP отличается от UDP?", "expected_section": "Сети > Транспортный уровень" },
  { "question": "…", "expected_section": ["Раздел А", "Раздел Б"], "source": "конспект.docx" }
]
```

`expected_section` — путь раздела или список равноценных путей, `source` —
имя файла, если одинаковый раздел есть в нескольких конспектах.
Пример формата — `questions.example.json`.

Метрики по каждой стратегии:

- число чанков; длина в символах: min, median, p95, max (ближайший ранг);
- доля чанков, пересекающих границу раздела: абзацы чанка не лежат в одном
  поддереве разделов (вводный текст раздела вместе с его подразделом — не
  пересечение, соседние разделы — пересечение);
- доля чанков, обрезанных посреди предложения: конец не совпадает ни с
  концом абзаца, ни со знаком `.`, `!`, `?`, `…` (начало не проверяется —
  у окон с перекрытием оно внутри предложения по построению);
- время эмбеддинга;
- hit@1, hit@5 и MRR: попадание — `section` найденного чанка совпадает с
  ожидаемым; «раздела нет среди чанков» считает вопросы, которые попасть
  не могли, потому что стратегия склеила их раздел с соседним.

Вывод в отчёте собирается по фиксированным правилам из тех же чисел, что в
таблице, — текст не расходится с цифрами. Толкование лучше дописать руками
после прогона.

## Решения

**SQLite, а не FAISS или JSON.** Корпус конспектов — сотни чанков, и
перебор косинусом по всем векторам в памяти занимает миллисекунды, так что
ANN-индекс ничего не даёт, а тянет Python или C++. JSON не даёт транзакций
и запросов: нельзя атомарно заменить одну стратегию, проверить, что у
каждого чанка есть вектор, или увидеть смесь моделей одним `select`.
SQLite — один файл, `sqlx` с миграциями, как у `activity-mcp`.

**`nomic-embed-text` и её ограничения.** Модель на 137M параметров
(≈ 270 МБ, вектор 768) выбрана ради слабого ноутбука. Она обучена в
основном на английском, а конспекты на русском, поэтому абсолютные hit@k и
MRR ожидаемо невысокие. Сравнение стратегий от этого остаётся честным:
модель, префиксы и вопросы у обеих общие. Замена на многоязычную модель
(например, `bge-m3`) — отдельное решение: другая размерность и заметно
больший вес.

**Префиксы `search_document:` / `search_query:`.** `nomic-embed-text`
обучена с префиксом задачи: без него векторы документов и вопросов
попадают в разные области пространства и поиск деградирует. Префикс
добавляется только к входу модели, в `text` чанка он не пишется.

**Контекст модели, `num_ctx` и `truncate: false`.** По умолчанию Ollama
молча обрезает вход длиннее контекста — вектор длинного раздела описывал
бы только его начало. `truncate: false` превращает такой вход в явную
ошибку `the input length exceeds the context length`; `index-mcp` тогда
пересылает батч по одному входу и называет `chunk_id` и длину чанка,
который не поместился. Контекст `nomic-embed-text` — 2048 токенов
(`nomic-bert.context_length` в метаданных модели), и `options.num_ctx`
больше этого его не расширяет: первый живой прогон с `num_ctx = 8192` и
`--max-section 3000` упал на разделах русского конспекта: словарь модели
в основном английский, кириллица дробится на мелкие токены, и раздел в
3000 символов выходит за 2048 токенов. Поэтому умолчания — `--num-ctx 2048` и
`--max-section 1500` (у `fixed` окна по 1200 символов в этот контекст
помещаются). Нативный `/api/embed` выбран вместо OpenAI-совместимого
`/v1/embeddings` ради `truncate` и `options`.

**`serve` — новая подкоманда поверх тех же функций.** `build` и `compare`
сохранили имена, флаги и умолчания (теперь они лежат константами в
`main.rs::defaults`, откуда их берут и clap, и инструмент). `index_build`
зовёт `run_build` с теми же структурами, что clap собирает из флагов, а
`index_compare` — `run_compare`; ни chunking, ни эмбеддинг, ни хранилище не
скопированы. Единственное добавление в `run_build` — строки хода в stderr.

**Размерность новой модели.** Умолчание `--dim 768` верно только для
`nomic-embed-text`. Инструмент `index_build` без `dim` берёт длину вектора из
`/api/show` (`<arch>.embedding_length`), а если Ollama её не сообщил — из
длины первого вектора (`Embedder::probe_dim`). Эмбеддер по-прежнему сверяет
каждый вектор с этой размерностью. У CLI-флага `--dim` умолчание прежнее.

**`index_compare` пишет отчёт туда, куда сказано.** У `out` нет умолчания:
иначе вызов без аргумента перезаписал бы `docs/chunking-comparison.md`,
который воспроизводит записанные цифры. Клиент `agentcli` этот инструмент
модели не отдаёт.

**Токенизатор внутри, а не отдельный словарь.** Счёт токенов повторяет
WPM-токенизатор llama.cpp: NFD с удалением диакритики (`й` → `и`), нижний
регистр, пунктуация отдельными словами, жадный поиск самых длинных токенов
после «фантомного пробела» `▁`, слово без разбора — один `[UNK]`. Словарь
приходит из того же Ollama, поэтому модель и счёт не расходятся, а
скачивать `tokenizer.json` с Hugging Face не нужно. Точное совпадение с
Ollama до токена не гарантировано (классы пунктуации Unicode взяты
приближённо), поэтому живой тест сверяет счёт с `prompt_eval_count`
Ollama с допуском в 2 токена, а переполнение всё равно ловит
`truncate: false`.

**Как определяются заголовки.** Не по `styleId`: в русском Word id стиля
«Заголовок 1» — `1`, в английском — `Heading1`. Уровень берётся из
`styles.xml`: имя стиля `heading 1`…`heading 9` (Word пишет его
по-английски в любой локализации; русское `заголовок N` тоже принимается),
иначе `w:outlineLvl` стиля, с наследованием через `w:basedOn`.
`w:outlineLvl` прямо в абзаце имеет приоритет над стилем. Документ без
стилей заголовков даёт `structure` без разделов — это стоит отметить в
отчёте, а не подгонять.

**Что читается из `.docx`.** Только `word/document.xml`: сноски и
колонтитулы лежат в отдельных частях архива и пропускаются. Таблица —
строка на ряд, ячейки через ` | `. Запасные копии надписей (`mc:Fallback`)
и перемещённый текст (`w:moveFrom`) пропускаются, чтобы текст не задваивался.

## Тесты

```bash
cargo test
cargo clippy --all-targets -- -D warnings
```

Тесты не ходят в настоящий Ollama: `/api/embed` подменяет `wiremock`, а
сквозной тест `build` → `compare` использует поддельный эмбеддер «мешок
слов», при котором вопросы находят свои разделы. `.docx` собираются в
памяти, двоичных файлов в репозитории нет.

Протокол `serve` проверяет `tests/protocol.rs`: настоящий процесс
`index-mcp serve`, клиент `rmcp`, Ollama подменён `wiremock` (в том числе
`/api/tags` и `/api/show`). Он проверяет цепочку `index_build` →
`index_status` → `index_search` → `index_compare`, отказ поиска при другой
модели, размерность новой модели (из `/api/show` и из первого вектора) и
умолчания `build`.

Живой тест против Ollama с `nomic-embed-text` (заодно сверяет счёт токенов
с `prompt_eval_count` Ollama):

```bash
INDEX_MCP_OLLAMA_URL=http://localhost:11434 cargo test live_ollama -- --ignored
```

Исходные конспекты в репозиторий не кладутся: `.gitignore` исключает
`*.docx`, `*.db` и каталог `data/`.
