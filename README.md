# index-mcp-agent

Локальный индекс конспектов `.docx` для поиска по смыслу. `index-mcp`
читает каталог с `.docx`, режет текст на чанки двумя стратегиями
(`fixed` и `structure`), получает эмбеддинги у локального
[Ollama](https://ollama.com) и складывает чанки с векторами в SQLite. Вторая
команда сравнивает стратегии на вопросах к конспектам и пишет отчёт
`docs/chunking-comparison.md`.

Внешних сервисов, кроме Ollama, нет: ни Python, ни FAISS, ни облачных API.
Ближайшие соседи ищутся перебором косинусом в Rust. MCP-инструмента поиска
по индексу пока нет: сервер живёт в каталоге `mcp/` зонтичного репозитория
[agent](https://github.com/Egor-Liadsky/agent), и инструмент — следующий
шаг. С консольным клиентом `agentcli` сервер cargo-зависимостью не связан.

## Устройство

Cargo workspace (Rust edition 2024) из одного крейта:

| Крейт       | Каталог        | Что это                         |
|-------------|----------------|---------------------------------|
| `index-mcp` | `crates/index` | бинарник `index-mcp`: `build` и `compare` |

- `src/main.rs` — флаги CLI, обход каталога, индексатор (чанки →
  эмбеддинги → хранилище) и команда `compare`;
- `src/docx.rs` — абзацы `.docx` с уровнем заголовка и смещениями;
- `src/chunk/mod.rs` — трейт `Chunker`, реестр стратегий и метрики границ;
- `src/chunk/fixed.rs`, `src/chunk/structure.rs` — две стратегии;
- `src/embed.rs` — клиент `POST /api/embed` Ollama;
- `src/store.rs` — SQLite через `sqlx`, миграции в `migrations/`;
- `src/compare.rs` — метрики, hit@k, MRR и отчёт в Markdown.

| Назначение           | Крейты                         |
|----------------------|--------------------------------|
| Асинхронный рантайм  | `tokio`                        |
| CLI                  | `clap`                         |
| Чтение `.docx`       | `zip`, `quick-xml`             |
| HTTP к Ollama        | `reqwest` (rustls)             |
| Индекс               | `sqlx` (SQLite, migrate)       |
| Сериализация, ошибки | `serde`, `serde_json`, `anyhow`|
| Тесты                | `wiremock`, `tempfile`         |

Стратегия — реализация трейта `Chunker` (`name`, `params`, `chunk`).
Индексатор, эмбеддер и хранилище работают со списком `Box<dyn Chunker>`,
поэтому новая стратегия — это файл в `src/chunk/` и строка в `chunk::make`,
без правок остального кода.

## Установка и запуск

```bash
ollama pull nomic-embed-text                # один раз
cargo build --release

./target/release/index-mcp build --input ~/notes --db index.db --strategy all
./target/release/index-mcp compare --db index.db --questions questions.json
```

`build` печатает по строке на стратегию: число чанков, файлов, символов и
время эмбеддинга. `compare` печатает отчёт и записывает его в `--out`.

Проверка базы после `build`:

```bash
sqlite3 index.db "select strategy, count(*) from chunks group by strategy;
  select count(*) from chunks c left join embeddings e using(chunk_id) where e.chunk_id is null;
  select distinct model, dim from embeddings;"
```

Второе число — 0 (у каждого чанка есть вектор), третий запрос — одна строка
`nomic-embed-text|768`.

### `build`

| Флаг            | Умолчание    | Что задаёт |
|-----------------|--------------|------------|
| `--input`       | —            | каталог с `.docx`, обходится рекурсивно; скрытые каталоги и lock-файлы `~$*.docx` пропускаются |
| `--db`          | `index.db`   | файл SQLite, создаётся при первом запуске |
| `--strategy`    | `all`        | `fixed`, `structure` или `all` |
| `--chunk-size`  | `1200`       | `fixed`: размер окна в символах |
| `--overlap`     | `200`        | `fixed`: перекрытие окон, меньше половины окна |
| `--max-section` | `3000`       | `structure`: раздел длиннее режется по абзацам |
| `--min-section` | `200`        | `structure`: кусок короче склеивается со следующим |
| `--min-chars`   | `50000`      | минимальный объём корпуса; меньше — ошибка с числом символов |

### `compare`

| Флаг          | Умолчание                     | Что задаёт |
|---------------|-------------------------------|------------|
| `--db`        | `index.db`                    | база, построенная `build` |
| `--questions` | `questions.json`              | вопросы с ожидаемыми разделами |
| `--out`       | `docs/chunking-comparison.md` | куда записать отчёт |

### Общие флаги эмбеддинга

| Флаг             | Умолчание                | Что задаёт |
|------------------|--------------------------|------------|
| `--ollama-url`   | `http://localhost:11434` | адрес Ollama |
| `--model`        | `nomic-embed-text`       | модель эмбеддингов |
| `--doc-prefix`   | `search_document: `      | префикс задачи перед текстом чанка |
| `--query-prefix` | `search_query: `         | префикс задачи перед вопросом |
| `--batch`        | `32`                     | текстов в одном запросе |
| `--num-ctx`      | `8192`                   | контекст модели, `options.num_ctx` |
| `--dim`          | `768`                    | ожидаемая размерность; другая — ошибка |

`compare` отказывается работать, если база построена другой моделью или
размерностью, чем указаны флаги: векторы разных моделей несравнимы.

## Стратегии chunking

**`fixed`** — окна по `--chunk-size` символов с перекрытием `--overlap`.
Конец окна ищется в его последней четверти: сначала конец предложения или
абзаца, затем пробел, и лишь без них — жёсткий разрез. Начало следующего
окна — начало предложения рядом с точкой «конец минус перекрытие», иначе
начало слова. `section` — путь последнего заголовка перед началом чанка.

**`structure`** — раздел от заголовка до следующего заголовка того же или
более высокого уровня, вместе с подразделами:

- раздел целиком не длиннее `--max-section` — один чанк;
- длиннее — собственный текст раздела (заголовок и абзацы до первого
  подраздела) режется по границам абзацев, подразделы — рекурсивно тем же
  правилом; абзац длиннее `--max-section` режется по концам предложений;
- кусок короче `--min-section` склеивается со следующим куском того же
  родителя, последний — с предыдущим; `section` склейки — раздел её большей
  части, чтобы заголовок с одной вводной фразой не забирал себе текст
  первого подраздела;
- заголовок входит в текст чанка, а продолжению длинного раздела
  дописывается первой строкой; `char_start`/`char_end` указывают на
  фрагмент документа без дописанного заголовка.

Текст до первого заголовка получает пустой `section`.

`chunk_id` — `{strategy}:{имя файла без расширения}:{ordinal:04}`, `ordinal`
считается внутри файла. Повторный `build` на тех же файлах и флагах даёт те
же id. Одинаковые имена файлов в разных подкаталогах — ошибка: id совпали бы.

## Схема БД

```sql
chunks (chunk_id TEXT UNIQUE, strategy, source, title, section, ordinal,
        char_start, char_end, text, crosses_section, cut_mid_sentence)
embeddings (chunk_id → chunks, model, dim, vector BLOB)   -- f32 little-endian
builds (strategy PRIMARY KEY, model, dim, files, chars, chunks, embed_ms,
        params, built_at)
```

- `source` — путь к файлу, `title` — `dc:title` из `docProps/core.xml`,
  иначе имя файла; `section` — путь заголовков `Раздел > Подраздел`;
  смещения — в символах общего текста документа (абзацы через `\n`);
- в `text` префикс задачи не пишется, он уходит только в модель;
- `crosses_section` и `cut_mid_sentence` считаются при построении: после
  него структуры документа в базе нет;
- `builds` хранит последнее построение стратегии: объём корпуса, время
  эмбеддинга и параметры (размеры стратегии, `doc_prefix`, `num_ctx`);
- `build` стратегии заменяет её строки одной транзакцией, другие стратегии
  не трогает. Эмбеддинг идёт до транзакции, поэтому недоступный Ollama
  оставляет прежний индекс целым.

## Сравнение и `questions.json`

```json
[
  { "question": "Чем TCP отличается от UDP?", "expected_section": "Сети > Транспортный уровень" },
  { "question": "…", "expected_section": ["Раздел А", "Раздел Б"], "source": "конспект.docx" }
]
```

`expected_section` — путь раздела или список равноценных путей, `source` —
имя файла, если одинаковый раздел есть в нескольких конспектах.
Пример формата — `questions.example.json`.

Метрики по каждой стратегии:

- число чанков; длина в символах: min, median, p95, max (ближайший ранг);
- доля чанков, пересекающих границу раздела: абзацы чанка не лежат в одном
  поддереве разделов (вводный текст раздела вместе с его подразделом — не
  пересечение, соседние разделы — пересечение);
- доля чанков, обрезанных посреди предложения: конец не совпадает ни с
  концом абзаца, ни со знаком `.`, `!`, `?`, `…` (начало не проверяется —
  у окон с перекрытием оно внутри предложения по построению);
- время эмбеддинга;
- hit@1, hit@5 и MRR: попадание — `section` найденного чанка совпадает с
  ожидаемым; «раздела нет среди чанков» считает вопросы, которые попасть
  не могли, потому что стратегия склеила их раздел с соседним.

Вывод в отчёте собирается по фиксированным правилам из тех же чисел, что в
таблице, — текст не расходится с цифрами. Толкование лучше дописать руками
после прогона.

## Решения

**SQLite, а не FAISS или JSON.** Корпус конспектов — сотни чанков, и
перебор косинусом по всем векторам в памяти занимает миллисекунды, так что
ANN-индекс ничего не даёт, а тянет Python или C++. JSON не даёт транзакций
и запросов: нельзя атомарно заменить одну стратегию, проверить, что у
каждого чанка есть вектор, или увидеть смесь моделей одним `select`.
SQLite — один файл, `sqlx` с миграциями, как у `activity-mcp`.

**`nomic-embed-text` и её ограничения.** Модель на 137M параметров
(≈ 270 МБ, вектор 768) выбрана ради слабого ноутбука. Она обучена в
основном на английском, а конспекты на русском, поэтому абсолютные hit@k и
MRR ожидаемо невысокие. Сравнение стратегий от этого остаётся честным:
модель, префиксы и вопросы у обеих общие. Замена на многоязычную модель
(например, `bge-m3`) — отдельное решение: другая размерность и заметно
больший вес.

**Префиксы `search_document:` / `search_query:`.** `nomic-embed-text`
обучена с префиксом задачи: без него векторы документов и вопросов
попадают в разные области пространства и поиск деградирует. Префикс
добавляется только к входу модели, в `text` чанка он не пишется.

**`num_ctx` и `truncate: false`.** По умолчанию Ollama даёт модели 2048
токенов и молча обрезает вход длиннее контекста — вектор раздела
структурной стратегии описывал бы только его начало. Поэтому в запросе
`options.num_ctx = 8192`, а `truncate: false` превращает слишком длинный
вход в явную ошибку. Нативный `/api/embed` выбран вместо
OpenAI-совместимого `/v1/embeddings` именно ради этих двух параметров.

**Как определяются заголовки.** Не по `styleId`: в русском Word id стиля
«Заголовок 1» — `1`, в английском — `Heading1`. Уровень берётся из
`styles.xml`: имя стиля `heading 1`…`heading 9` (Word пишет его
по-английски в любой локализации; русское `заголовок N` тоже принимается),
иначе `w:outlineLvl` стиля, с наследованием через `w:basedOn`.
`w:outlineLvl` прямо в абзаце имеет приоритет над стилем. Документ без
стилей заголовков даёт `structure` без разделов — это стоит отметить в
отчёте, а не подгонять.

**Что читается из `.docx`.** Только `word/document.xml`: сноски и
колонтитулы лежат в отдельных частях архива и пропускаются. Таблица —
строка на ряд, ячейки через ` | `. Запасные копии надписей (`mc:Fallback`)
и перемещённый текст (`w:moveFrom`) пропускаются, чтобы текст не задваивался.

## Тесты

```bash
cargo test
cargo clippy --all-targets -- -D warnings
```

Тесты не ходят в настоящий Ollama: `/api/embed` подменяет `wiremock`, а
сквозной тест `build` → `compare` использует поддельный эмбеддер «мешок
слов», при котором вопросы находят свои разделы. `.docx` собираются в
памяти, двоичных файлов в репозитории нет.

Живой тест против Ollama с `nomic-embed-text`:

```bash
INDEX_MCP_OLLAMA_URL=http://localhost:11434 cargo test live_ollama -- --ignored
```

Исходные конспекты в репозиторий не кладутся: `.gitignore` исключает
`*.docx`, `*.db` и каталог `data/`.
